# Selfit P0 需求验收标准与验收 Case 集合

日期：2026-09-04
适用范围：单品与穿搭内容、16 人格适配、首页推荐稳定性、款式去重、试穿往返体验
结论口径：本文是本轮 P0 的唯一验收清单；**色彩测试、色彩诊断准确率、色板命中均不在本轮范围内**。

## 1. P0 放行原则

P0 采用“硬门禁”，不做总分平均。以下八个门禁全部通过，才允许进入内部灰度：

| 门禁 | 验收目标 | 放行标准 |
|---|---|---|
| G0 可追溯 | 代码、内容、图片、审核、推荐版本能互相对应 | 版本清单完整，任一素材变化会使旧审核失效 |
| G1 首页稳定 | 不再出现返回首页后卡片和请求失控增长 | 所有 FEED Case 通过，10 分钟稳定性测试无异常 |
| G2 内容准入 | 首页只出现当前版本且完成四道审核的内容 | 160 套锚点 100% 四门通过；待审、拒绝、过期内容 0 曝光 |
| G3 锚点完整 | 16 人格各有 10 套可用且有结构差异的锚点 | 160/160 通过结构、主角、场景、去重和文案检查 |
| G4 人格可辨 | 独立审核者在不知道答案时能读出人格 | 总体 Top-1 ≥70%、Top-2 ≥90%；逐人格 Top-1 ≥60%、Top-2 ≥80% |
| G5 推荐质量 | 推荐不靠重复款、未审内容或错人格凑数 | 首 10 套主人格 ≥8，兼容人格 ≤2；全部去重约束通过 |
| G6 端到端体验 | 浏览、反馈、试穿、返回均连续可用 | 目标设备 Case 全过，无横向溢出、阻断错误或错误跳转 |
| G7 性能与回归 | 关键响应有量化基线，改动不引入新失败 | 全部 PERF Case 通过，非色彩链路无新增失败 |

任何一个 P0 Case 为 `Fail`、`Blocked` 或 `Not Run`，对应门禁都不得记为通过。允许缩小灰度范围，但不允许用“整体体验尚可”覆盖硬门禁失败。

## 2. 统一验收口径

### 2.1 Case 状态

- `Pass`：预期结果全部满足，证据齐全。
- `Fail`：至少一个预期结果不满足。
- `Blocked`：环境或数据阻塞，尚未验证；不等同于通过。
- `Not Run`：未执行；不等同于通过。

### 2.2 必须冻结的版本

每次验收建立一份 release manifest，至少记录：

- Git commit；
- 内容池版本及内容文件 SHA-256；
- 160 套锚点清单版本；
- 单品、穿搭图片 SHA-256；
- 视觉审核索引版本；
- 款式家族表版本；
- 独立盲审包版本和答案表版本；
- 推荐策略版本；
- 人格算法版本，仅记录、不在本轮修改。

验收中任何图片、配方、人格归属、审核字段或款式家族发生变化，受影响 Case 必须重跑；不能继承旧结论。

### 2.3 证据层级

| 层级 | 能证明什么 | 不能替代什么 |
|---|---|---|
| 自动化测试 | 规则、状态、版本和接口行为符合预期 | 不能证明衣服好看或人格可辨 |
| 逐套内容审核 | 当前图片与配方在技术、审美、人格、场景上可用 | 不能证明独立观察者能猜中人格 |
| 独立盲审 | 不看答案时的人格辨识效果 | 不能证明页面和请求稳定 |
| 浏览器端到端 | 用户路径、布局、请求和状态恢复正常 | 不能替代内容审核 |
| 性能采样 | 指定环境下的响应和渲染速度 | 不能外推到所有网络与设备 |

## 3. P0 需求验收标准

### P0-1 首页信息流稳定性

1. 首页只有在当前页面可见、用户接近列表尾部且没有在途请求时才加载下一批。
2. 同一游标最多发起一个有效请求；重试、快速切人格和旧响应不得产生重复卡片。
3. 离开首页进入试穿后，后台不得继续触发推荐分页。
4. 返回首页后恢复原滚动锚点；恢复期间观察器不得误触发连续加载。
5. 当前会话列表 DOM 最多保留 60 张推荐卡，回收卡片不能造成明显跳动。
6. 候选耗尽后返回 `has_more=false`，不允许用重复、错人格或未审核内容填满。
7. 试穿任务完成只更新任务状态，不强制把用户从当前页面跳走。

### P0-2 内容四门准入

每一套正式锚点必须同时通过以下四门：

1. 技术门：图片可访问、无明显裁切/透明底/配对鞋/层级遮挡错误，引用单品都存在。
2. 审美门：整套只有一个清晰视觉主角，其余单品形成支撑；无明显季节、正式度或搭配冲突。
3. 人格门：人格证据来自主衣廓形、材质、结构和整套关系，不能只靠名字、颜色或鞋包配件证明。
4. 场景门：默认推荐适合日常/通勤/约会等标注场景；礼服、主题造型和实验款不得伪装成默认日常。

四门状态只允许 `pass / needs_review / reject`。正式池只接纳当前版本的四门全 `pass`；任何缺失、格式错误、旧版本、`needs_review` 或 `reject` 都必须失败关闭。

### P0-3 160 套人格锚点

1. 16 个人格各 10 套，共 160 套，不多不少。
2. 每人格包含 4 套入门、4 套典型、2 套轻探索。
3. 每人格 10 套覆盖裤装、裙装、连衣装三类主结构；单一结构不得超过 5 套。
4. 160 套使用 160 个不同父配方；同人格内同一主单品最多 2 次、同一家族最多 2 次。
5. 每套只有一个主视觉；配饰不能独自承担人格表达。
6. 所有叠穿关系显式记录，不能以空 `layer_graph` 默认为合理。
7. 用户端标题和解释使用自然语言，不出现内部人格代码、provider、pipeline、confidence、JSON 等实现词。
8. 本轮只验收这 160 套，不要求先把 600 件单品、1,200 套穿搭全部升级为合格内容。

### P0-4 独立人格盲审

1. 审核包隐藏人格名、源文件名、生成提示、既有评分和答案映射。
2. 审核者必须不是该批内容的生产者，并提交独立性和未见答案声明。
3. 每套必须填写两个不同人格的 Top-1/Top-2、视觉理由、问题项及 `accept/reject/uncertain`。
4. 总体 Top-1 命中率 ≥70%，Top-2 命中率 ≥90%。
5. 每个人格 Top-1 命中率 ≥60%，Top-2 命中率 ≥80%，避免用强势人格拉高总体平均。
6. 160 套中 `reject=0`；`uncertain` 必须由第二位独立审核者复核并形成最终结论。
7. 盲审达标不自动发布；仍需四门准入和端到端门禁通过。

### P0-5 推荐适配与丰富度

1. 正式推荐只使用当前版本的 160 套合格锚点；未审核库存不得作为兜底。
2. 每个正式人格的前 10 套中，主人格锚点至少 8 套，兼容人格最多 2 套；不得出现非兼容人格。
3. 前 10 套覆盖裤装、裙装、连衣装；单一结构最多 5 套。
4. 首屏 6 套中同一父配方最多 1 套；任意连续 10 套同一主单品最多 2 次、同一款式家族最多 2 次。
5. 同一父配方的变体之间至少间隔 8 个位置；相邻两批各 6 套的重复内容最多 1 套。
6. “不喜欢”后当前卡立即移除并补位；被否定的穿搭、本次主单品和对应近似家族不得在当前会话紧邻重现。
7. 请求幂等、分页快照稳定；账号、正式人格和测试人格互不污染。
8. 供给不足时允许返回少于目标数量并明确耗尽，不允许降低审核或人格门槛凑数。

### P0-6 最小款式家族表

1. 160 套锚点涉及的所有主服装必须 100% 映射到款式家族或明确的 singleton。
2. 家族关系必须绑定当前图片证据、类别和审核版本；不同大类单品不得合并。
3. 机器候选、同名描述或历史关系不能自动升级为正式家族，需要复核结论。
4. 图片或类别变化后，相关家族关系自动过期，不继续参与去重。
5. 家族表损坏或缺失时采用保守 singleton 回退，同时仍执行主单品 ID 和父配方去重。

### P0-7 端到端与性能

1. 验收宽度：390px、393px、430px、1440px 桌面居中移动壳体。
2. 核心路径：进入首页 → 浏览与换一批 → 查看详情 → 反馈 → 发起试穿 → 返回首页 → 任务完成 → 查看结果。
3. 全路径无横向溢出、文字遮挡、按钮裁切、坏图、控制台未处理异常和重复资源错误。
4. 推荐接口在固定内网环境、预热后 50 次请求的 P95 ≤1 秒。
5. 首屏 6 张图中可视图片加载完成 P95 ≤2.5 秒；换一批点击后 300ms 内出现明确反馈。
6. 从试穿页返回首页后 500ms 内完成列表与滚动锚点恢复。
7. 首页静置 30 秒推荐请求数为 0；完整往返 10 次后卡片数不超过 60，请求次数与用户触底次数同阶增长。

## 6. 验收执行顺序

1. 冻结候选 commit、160 套锚点、图片及全部版本，生成 release manifest。
2. 跑 B/C/F：内容四门、锚点结构、款式家族。失败项先返工，避免把不合格内容送盲审。
3. 生成全新匿名包，完成 D：独立盲审。任何素材返工后重新生成并重审受影响样本。
4. 基于已通过内容跑 E：16 人格推荐矩阵、分页和负反馈检查。
5. 跑 A/G/H：首页稳定、端到端、设备和性能。
6. 跑 P0 相关回归和全量非色彩回归，汇总证据。
7. 产品、设计、研发、QA 四方对 release report 签字；全部门禁通过后再申请内部灰度。
